# $pend Backend Context

## Purpose

- This file is the backend/server source-of-truth for agent work on $pend.
- The backend is a Gin-routed JSON API (`server/internal/api`) with no server-rendered HTML, no templates, and no separate session-cookie auth — a client (today, `client/`'s React SPA) talks to it entirely over `/api/v1/*` with a JWT access token plus a refresh-token cookie.
- The most complete flow is the core ledger: creating/editing/deleting transactions and categories, the dashboard, the full auth lifecycle (register/login/refresh/logout/forgot-reset-password/email verification), settings, and CSV import/export.

## Stack

- Language/runtime: Go (see `server/go.mod` for the exact version, currently `1.26.5`).
- Router: `gin-gonic/gin`, with `gin-contrib/cors` for cross-origin requests from `client/`.
- Rendering: none. Every response is JSON (or, for CSV export, `text/csv`); there is no HTML, no templates, no server-side rendering of any kind.
- Database: PostgreSQL via `pgx/v5` (`jackc/pgx/v5`); hand-written SQL in `server/internal/database/queries`, Go bindings generated by `sqlc` into `server/internal/sqlcgen` (never hand-edited).
- Migrations: `golang-migrate/migrate/v4`, applied automatically at server startup — no separate migrate step.
- Auth: a stateless, signed JWT access token (15 min TTL) plus a refresh token that reuses the pre-existing opaque session-row design (7-day TTL, stored in `sessions`, sent as an httpOnly cookie) — see Authentication Model below.
- Email: Brevo's HTTP API (`server/internal/mailer`) for password-reset/verification mail.
- CSV: `server/internal/csvimport` (sniffing/mapping/planning, no database access) backs the import/export endpoints.

## Main Business Scope Right Now

- Each user account is independent — no bill-splitting, no shared budgets, no organizations or teams.
- Core ledger: creating, editing, and deleting transactions and categories; a dashboard with month totals, a carried-over balance, a category breakdown, and a 4-month series; a paged/filterable transaction list; CSV import/export.
- Account lifecycle: register, login (with a 5-attempt/15-minute lockout), logout, forgot/reset password, email verification (non-blocking), settings (profile, email, password, theme, active sessions, account deletion with hard delete).
- Authorization is single-tier: there is no admin role and no roles/permissions system at all — every authenticated user has exactly the same capabilities, scoped to their own `user_id` in every query.

## What Is Actually Implemented

Every route is under `/api/v1`, except `GET /healthz` at the root (Render's health check and the keep-alive cron probe that exact path — keep it there). Public:

- `POST /api/v1/register`, `POST /api/v1/login`, `POST /api/v1/refresh`, `POST /api/v1/logout`
- `POST /api/v1/forgot-password`, `GET|POST /api/v1/reset-password`
- `POST /api/v1/verify-email`

Authenticated (behind `internal/api.RequireAuth`, an `Authorization: Bearer <access token>` header):

- `GET /api/v1/me`
- Categories: `GET|POST /api/v1/categories`, `PATCH|DELETE /api/v1/categories/{id}`
- Transactions: `GET|POST /api/v1/transactions`, `PATCH|DELETE /api/v1/transactions/{id}`, `GET /api/v1/transactions/export`, `POST /api/v1/transactions/import`
- `GET /api/v1/dashboard`
- Settings: `GET /api/v1/settings`, `PATCH /api/v1/settings/profile`, `PATCH /api/v1/settings/email`, `POST /api/v1/settings/resend-verification`, `PATCH /api/v1/settings/password`, `POST /api/v1/settings/delete-account`, `DELETE /api/v1/settings/sessions/{id}`, `POST /api/v1/settings/sessions/revoke-others`, `PUT /api/v1/settings/theme`

## Important Reality Checks

- Authorization is single-tier — see Main Business Scope above. There is no roles/permissions system to audit for missing checks.
- Email verification gates nothing (`email_verified` only matters once a client shows a reminder for it — see `.claude/rules/email-verification.md`'s known gap) — deliberate, not an oversight to "fix".
- The default-category history (migrations 000005 → 000006 → 000008 → 000014) is deliberately append/update-in-place, never delete-and-reinsert, because `transactions.category_id` has no `ON DELETE` clause. See Seeder Reality below before "cleaning up" an odd-looking default category.
- This backend was migrated off an older Chi-routed, `html/template`-rendered monolith. That code (`internal/handlers`, `internal/web`, `internal/csrf`) is deleted, not archived elsewhere in this repo — git history is where it still exists, if you need to see how something used to work.

## Backend Layout

- `server/cmd/server/`: entrypoint; wires `api.Deps`, applies pending migrations, starts the HTTP server.
- `server/internal/api/`: every HTTP handler — one flat package, grouped by filename prefix: `router.go` (the full route table, CORS), `middleware.go` (`RequireAuth`, `UserID`), `auth_handlers.go` (register/login/refresh/logout, `issueAuthResponse`), `password_reset_handlers.go` (forgot/reset-password, email verification), `category_handlers.go`, `transaction_handlers.go` + `transaction_query.go` (filters/month-scope/paging value objects), `dashboard_handlers.go`, `settings_handlers.go`, `import_handlers.go` + `export_handlers.go` (CSV). Keep the prefix when adding a file; a new area gets a new prefix rather than a bare name.
- `server/internal/database/migrations/`: numbered up/down SQL migration pairs — the real schema source of truth.
- `server/internal/database/queries/`: hand-written SQL; `server/internal/sqlcgen/` holds the `sqlc`-generated Go bindings (never hand-edited).
- `server/internal/auth/`: token issuance — `jwt.go` (stateless access tokens), `session.go` (the opaque refresh token/row), `password.go` (bcrypt), `lockout.go`, `password_reset.go`, `email_verification.go`.
- `server/internal/i18n/`: default-category display names, keyed by slug.
- `server/internal/format/`: `DeviceLabel` (User-Agent → "Chrome on Windows" for the active-sessions list) — the only formatter left; every display-string formatter the old HTML templates needed (money, dates, counts) was deleted along with them, since this API ships raw numbers and lets the client format them (see Request and Response Conventions below).
- `server/internal/txnrule/`: the numeric limits a transaction has to satisfy regardless of entry path (the transaction endpoints, the CSV importer).
- `server/internal/pgval/`: pgtype wrapper helpers.
- `server/internal/csvimport/`: CSV sniffing/mapping/planning, no database access.
- `server/internal/mailer/`: Brevo HTTP API client for transactional email.
- `server/render.yaml`: the Render Blueprint describing the web service deploy.

## Request and Response Conventions

- Every response except `/healthz` and the CSV export is a JSON envelope, `{"success": bool, "message": string, "data": T | null}`, written through `respondSuccess`/`respondError` in `response.go`; no endpoint answers `204`. See `.claude/rules/json-api-conventions.md` for the full set of conventions this package follows, several of them written up *because* a real bug violated them (never ship `null` for an array field a client expects `[]` from, never embed another package's untagged struct directly in a response).
- Ship raw numbers, not pre-formatted display strings. A money amount is a plain `int64` (VND, whole đồng), a percentage a plain `int`, a date `"2006-01-02"` — never a formatted `"50.000₫"` or a pre-composed sentence. The client owns formatting and i18n of its own UI text; this backend only resolves what it alone has the data for (a default category's display name via `i18n`, a User-Agent string via `format.DeviceLabel`).
- Authentication is a header, not a cookie, for every authenticated endpoint: `Authorization: Bearer <access token>`. The one exception is `POST /api/v1/refresh` and `POST /api/v1/logout`, which read the refresh-token httpOnly cookie instead — see Authentication Model.
- Every request body is capped at 1 MiB (`limitBody`, `maxRequestBytes` in `middleware.go`), the same as the CSV upload's own limit; a read past it fails and surfaces as the handler's usual 400.
- Localization: none — every message this API writes is English. Only default-category *names* are resolved through `server/internal/i18n`, keyed by a stable slug rather than the displayed string.

## Authentication Model

- Plain email+password login, no OAuth/SSO. Two tokens, not one:
  - **Access token** (`internal/auth/jwt.go`): a stateless, HS256-signed JWT naming a user ID, 15-minute TTL. Never checked against the database — it self-expires, and that's the entire point: it can't be revoked before it does, which is why it's kept short-lived.
  - **Refresh token**: the pre-existing opaque session-row token (`sessions` table, `internal/auth/session.go`), reused as-is rather than built as a second mechanism — see `jwt.go`'s doc comment for the full reasoning. Sent as an httpOnly, `Path=/api` cookie; 7-day TTL (`sessions.expires_at`).
- `POST /api/v1/refresh` exchanges a valid refresh-token cookie for a fresh access token without re-checking the password. It does not rotate the refresh token itself.
- A password change deletes every *other* session (refresh token) for the user but keeps the current one; "Log out everywhere else" in Settings calls the same deletion deliberately, as a user action rather than a side effect.
- Per-IP rate limits (`ratelimit.go`, in-memory token buckets, single instance): `login`, `reset-password` (GET and POST) and `verify-email` get a burst of 10 then 10 a minute; `register` and `forgot-password` share a burst of 5 then 5 an hour. Over budget answers `429` with `Retry-After`. `refresh` is not limited (its token is unguessable). The client IP is `c.ClientIP()`, trustworthy only because the router trusts no proxy unless `TRUSTED_PROXIES` names it. A second server instance would double every budget and need a shared store.
- Login lockout: 5 consecutive wrong passwords lock the account for 15 minutes (`users.failed_login_attempts`, `users.locked_until`), checked *before* password comparison so a locked account can't be used to extend its own lock. A completed password reset clears it.
- Password reset: `password_reset_tokens`, 1-hour TTL, single-use, emailed via Brevo. Resetting signs the visitor in (a fresh access token + refresh cookie), matching register/login.
- Email verification: `email_verification_tokens`, 24-hour TTL, shared by both signup confirmation and a settings email change (via `pending_email`, promoted onto `users.email` only once its own link is visited). Verification gates nothing — see Important Reality Checks.
- Account deletion is a hard delete (transactions → the account's own categories → the user row, in one transaction), not a soft `deleted_at` flag — see `.claude/rules/account-deletion.md`. The freed email can be re-registered immediately.
- The refresh-token cookie's `SameSite` must track `SecureCookies`, never a hardcoded `None` — see `.claude/rules/json-api-conventions.md` for why a hardcoded `None` silently broke every hard page reload in local dev.

## Authorization Model

- There is no role or permission system. Every authenticated request is scoped to `internal/api.UserID(c)`, and every query touching `transactions`, personal `categories`, or `sessions` filters by that user's own `user_id`.
- The only "shared" rows in the whole schema are the default categories (`categories.user_id IS NULL`) — readable and usable by every account, never writable by any of them.
- If a future feature needs per-user access tiers (an admin view, a shared household budget), there is currently nothing to build on — that would be new infrastructure, not a flag to flip.

## Core Data Model

- `users` — email (unique, login identity), password_hash (bcrypt), name, username (unique, `^[a-z][a-z0-9_]{2,19}$`), theme (`auto`/`light`/`dark`), email_verified + pending_email, failed_login_attempts + locked_until.
- `sessions` — id (opaque token, primary key, **this is the refresh token** — never send it to a client), public_id (UUID, the identifier clients see and send back to revoke a session), user_id, expires_at, created_at, user_agent (nullable — predates migration 000012).
- `categories` — user_id (NULL = shared default, else a personal category), name, type (`expense`|`income`), color (fixed 9-value palette via CHECK), slug (NULL for personal; a stable, unique, language-independent key for the 9 shared defaults — **match on this, never on `name`**). Unique index on `(user_id, type, name)`.
- `transactions` — user_id, category_id (FK to `categories`, **no `ON DELETE` clause**, deliberate — see below), amount (BIGINT, `CHECK (amount > 0)`, VND as a whole-number integer), type (`expense`|`income`), description, occurred_on (DATE).
- `password_reset_tokens`, `email_verification_tokens` — single-use token tables, FK to `users` with `ON DELETE CASCADE`.
- **`transactions.category_id` and `categories` have no `ON DELETE` clause between them, on purpose** — a category can't be deleted while transactions reference it without the app reassigning those rows first. Every migration that touches `categories` (000006, 000008, 000014) is written as an in-place UPDATE for exactly this reason.

## Transaction & Category Domain Rules

- A category's `color` must be one of the fixed 9-value palette (8 user-selectable plus 1 reserved gray for "Other"); enforced by a CHECK constraint, not just the API.
- A user cannot have two categories of the same `type` sharing a `name` — enforced by a unique index, `(user_id, type, name)`; NULL `user_id` rows (the shared defaults) are exempt, since Postgres treats NULL as always-distinct in a unique index.
- `amount` must be a positive integer (VND, no decimals) — enforced both by a DB `CHECK` and by `server/internal/txnrule`'s shared limits, which the transaction endpoints and CSV import both read from the same place rather than each re-stating the limit independently.
- A default category is identified by `slug`, never by `name` — the single most-repeated rule in the codebase (see Core Data Model above and `server/internal/i18n.CategoryName`).
- CSV import is all-or-nothing by design, never partial — see `.claude/rules/csv-import.md` for why.

## Seeder Reality

- There is no separate seeder step or seeder framework — default data is seeded by the migrations themselves, applied automatically at startup.
- The 9 shared default categories went through three migrations, not one: 000005 inserted an 8-category placeholder set; 000006 redesigned it in place to the current 9-category palette (renaming/recoloring existing rows rather than delete-and-reinsert, specifically so any account with history wasn't broken); 000008 gave each default its stable `slug` and renamed the Vietnamese display names to English.
- One historical wrinkle to know about: 000006 deleted the old "Thu nhập khác" (generic other-income) default *only if no transaction referenced it*; any account that already had one still has that row. 000014 re-adds an `other_income`-slugged default for the same conceptual slot (a now-deleted email-ingestion feature needed an "I don't know" bucket on the income side; the category itself was kept as a normal shared default after that feature was removed). Do not "clean up" either of these without checking whether it would orphan a real transaction.
- Conclusion: before touching a migration that inserts, updates, or deletes a default category, read 000005, 000006, 000008, and 000014 together — the current shape only makes sense as their sum.

## Setup and Run

- Backend install/run:

```bash
cd server
cp .env.example .env
go run ./cmd/server
```

- Requires `DATABASE_URL`, `JWT_SECRET` (generate with `openssl rand -base64 32`), etc. in `.env`, pointed at a locally installed Postgres (no Docker/compose setup is shipped, intentionally). `main.go` loads `.env` itself via `godotenv`; a variable already set in the environment still wins over the file.
- Migrations apply automatically at startup — there is no separate migrate step, for a fresh database or an already-migrated one restarting.
- Run tests (DB-touching tests are skipped unless `TEST_DATABASE_URL` is set; point it at a scratch database):

```bash
cd server
TEST_DATABASE_URL="postgres://USER:PASSWORD@localhost:5432/expense_tracker?sslmode=disable" go test ./...
```

- Checks that must stay clean before any commit:

```bash
cd server
go build ./...
gofmt -l .        # must print nothing
go vet ./...
golangci-lint run ./...   # config in server/.golangci.yml
```

- CI runs the same checks, plus `sqlc generate` leaving no diff, and runs the DB-backed tests against a Postgres 16 service container. The tests need the schema to exist before they start, and only `TestRunMigrations` (`cmd/server`) creates it, so CI runs that one test first (`go test -run '^TestRunMigrations$' ./cmd/server`). Do the same on a fresh scratch database, or packages race it and fail on a missing table.

- Regenerate `server/internal/sqlcgen` after changing SQL in `server/internal/database/queries` or the migrations:

```bash
cd server
sqlc generate
```

## Environment Variables That Matter

- `DATABASE_URL`, `PORT`, `SESSION_COOKIE_NAME`, `SECURE_COOKIES` — core wiring. `SESSION_COOKIE_NAME` names the refresh-token cookie (the name predates it being the only cookie this server sets). `SECURE_COOKIES=true` is required once served over HTTPS, or the refresh-token cookie is silently refused.
- `APP_BASE_URL` — scheme+host of **`client/`, not this server** — password-reset/verification emails link to its `/reset-password`/`/verify-email` React Router routes, which this API doesn't answer itself. Defaults to `http://localhost:5173` (Vite's default port); set to the Vercel domain in production.
- `BREVO_API_KEY`, `MAIL_FROM` — password-reset/verification email, sent over Brevo's HTTP API rather than SMTP, because Render's free tier blocks outbound SMTP ports but never 443. Optional — blank leaves forgot-password working end to end except the actual send, which is logged instead.
- `JWT_SECRET` — signs/verifies access tokens (`internal/auth/jwt.go`). Required, no fallback, same reasoning as `DATABASE_URL`: `config.Load()` refuses to start without it rather than sign tokens with a key baked into the source tree.
- `GIN_MODE` — set to `release` in `render.yaml`; Gin's default debug mode logs every route at startup. Leave unset locally.
- `CORS_ALLOWED_ORIGINS` — comma-separated origins the API's CORS middleware accepts credentialed cross-origin requests from (the `client/` deployment's domain). Optional; blank means none, correct until `client/` has a real deployment to allow.
- `TRUSTED_PROXIES` — comma-separated IPs/CIDRs of the reverse proxies whose `X-Forwarded-For` is believed when finding a client's IP for the rate limits. Blank trusts none (client = TCP peer), right locally. On Render it must name Render's proxy ranges or every visitor shares one budget; an invalid entry stops the server starting. See `render.yaml`.

## Deploy Notes

- Production target is a free Render web service on Render's native Go runtime — **no Dockerfile, by design** (see `server/render.yaml`'s own comments).
- Database is Neon Postgres, not Render's own free tier (which is deleted after 30 days). `DATABASE_URL` in Render must be Neon's *direct* (non-`-pooler`) connection string — golang-migrate's session-level advisory lock isn't supported by the pooled endpoint.
- `autoDeploy: true` on `main`; a schema change ships with the same push since the server migrates at startup. `rootDir: server` makes Render `cd` into `server/` before running `go build -o server ./cmd/server` / `./server` — this is a monorepo (`server/` + `client/`), the binary is built into and run from `server/`, not the repo root.
- `GET /healthz` (root, not under `/api`) doubles as the Render deploy health check and the target of an external cron that pings it every ~10 minutes to stop the free instance spinning down after 15 minutes of inactivity.
- `client/` deploys independently to Vercel — see `.claude/context/client.md` and `.claude/rules/deployment.md`. The two services have no shared deploy step; a push to one doesn't redeploy the other.

## Safe Edit Rules For Agents

- Never identify a default category by its displayed `name` — match on `slug`. This is the one rule repeated everywhere in this repo on purpose.
- Never delete-and-reinsert a default category in a migration; `transactions.category_id` has no `ON DELETE` clause, so any account with history would break. Update rows in place (see migrations 000006/000008/000014 for the pattern).
- Never let a response array field go out as JSON `null` where a client expects `[]`, and never embed another package's struct directly in a response without checking it carries JSON tags — see `.claude/rules/json-api-conventions.md`, both written up after a real browser-caught bug.
- When touching auth, re-check that the access-token TTL, the refresh-token cookie's `SameSite`/`Secure` pairing, and the lockout window all still agree — these pieces interact more than their separate file locations suggest.
- Follow `.claude/rules/go-conventions.md` for style; it is the one rules file that applies to every `.go` file in the repo.
- Verify a response-shape or cookie change with a real browser (or at minimum a real `fetch()`/`curl`), not just `go test` — `httptest` doesn't reproduce a browser's JSON-null-vs-`[]` handling or its cookie policy. See `.claude/rules/json-api-conventions.md`.

## Common Task Playbooks

- Add a new authenticated endpoint: add the route in `server/internal/api/router.go` inside the `RequireAuth` group, define request/response DTOs with explicit JSON tags (never embed an external struct without checking its tags), and add a DB-backed test in the matching `*_test.go` file.
- Add a new default category: do not do it by hand. Add it through a migration that follows the 000006/000008/000014 pattern (in-place update, an idempotent insert guarded by `WHERE NOT EXISTS`, a `slug` from day one), and update `server/internal/i18n` and `.claude/rules/categories.md`.
- Add a new environment variable: add it to `server/.env.example` with a comment explaining what leaving it blank does, to `server/render.yaml`'s `envVars` (with `sync: false` if it is a secret), and to this file's "Environment Variables That Matter".

## Known Gaps and Debt

- No admin/staff role, no audit log, no account-recovery window on deletion — deliberate scope cuts, not oversights (see Authorization Model and `.claude/rules/account-deletion.md`).
- No client-side reminder for an unverified email address, and `userDTO` doesn't carry `EmailVerified` yet — see `.claude/rules/email-verification.md`'s known gap.
- Test coverage is table-driven Go `testing` across packages, plus DB-backed integration tests in `internal/api` (`TEST_DATABASE_URL`).
