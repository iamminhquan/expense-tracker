# $pend Backend Context

## Purpose

- This file is the backend/server source-of-truth for agent work on $pend.
- $pend is a single Go monolith — there is no separate backend/frontend split to coordinate. `server/internal/handlers` renders server-side HTML (`html/template` + htmx) directly; there is no JSON API and no separate frontend client.
- The most complete flow today is the core ledger: creating/editing/deleting transactions and categories, the dashboard, and the full auth lifecycle (register/login/sessions/password reset/email verification), plus CSV import layered on top.

## Stack

- Language/runtime: Go (see `server/go.mod` for the exact version, currently `1.26.5`).
- Router: `chi` (`github.com/go-chi/chi/v5`) with `middleware.Logger` and `middleware.Recoverer`.
- Rendering: `html/template`, server-rendered pages, htmx for partial updates — no SPA, no separate frontend build, no JSON API for the UI to consume.
- Database: PostgreSQL via `pgx/v5` (`jackc/pgx/v5`); hand-written SQL in `server/internal/database/queries`, Go bindings generated by `sqlc` into `server/internal/sqlcgen` (never hand-edited).
- Migrations: `golang-migrate/migrate/v4`, applied automatically at server startup — no separate migrate step.
- Auth: hand-rolled cookie sessions, not a third-party auth library — see Authentication Model below.
- Email: Brevo's HTTP API (`server/internal/mailer`) for password-reset/verification mail.
- Frontend assets: Tailwind and Chart.js loaded from CDN, no JS build step; CSS/JS live in `server/internal/web/static/` and are `go:embed`ed into the binary.

## Main Business Scope Right Now

- Each user account is independent — no bill-splitting, no shared budgets, no organizations or teams.
- Core ledger: creating, editing, and deleting transactions and categories; a dashboard with month totals, a carried-over balance, a category doughnut, and a 4-month bar chart; a paged/filterable transaction list.
- Account lifecycle: register, login (with a 5-attempt/15-minute lockout), logout, forgot/reset password, email verification (non-blocking), settings (profile, email, password, theme, active sessions, account deletion with hard delete), CSRF via double-submit cookie on every mutation.
- One feature sits on top of the core ledger: CSV import (`server/internal/csvimport`).

## Important Reality Checks

- Authorization is single-tier: there is no admin role and no roles/permissions system at all — every authenticated user has exactly the same capabilities, scoped to their own `user_id` in every query. "Authorization Model" below states that fact; it is not a system to audit for missing checks.
- Email verification gates nothing (`email_verified` only drives a reminder banner) — deliberate (see `.claude/rules/email-verification.md`), not an oversight to "fix".
- The default-category history (migrations 000005 → 000006 → 000008 → 000014) is deliberately append/update-in-place, never delete-and-reinsert, because `transactions.category_id` has no `ON DELETE` clause. See Seeder Reality below before "cleaning up" an odd-looking default category.

## Backend Layout

- `server/cmd/server/`: entrypoint; wires `handlers.Deps`, applies pending migrations, starts the HTTP server.
- `server/internal/handlers/`: all HTTP handlers — one flat package (Go allows no other shape, and most of its files are `_test.go` siblings), grouped by filename prefix instead: `app_` (wiring: `Deps`, the router, the end-to-end smoke test), `auth_` (pre-login: login/register, password reset, email verification, lockout), `balance_` (the header balance widget), `category_` (the categories page), `import_` (CSV import), `report_` (the dashboard), `req_` (request value objects: month/scope, filters, paging), `settings_` (the settings page), `txn_` (the transactions page), `view_` (the render seam, the template `FuncMap`, the layout invariant tests). Keep the prefix when adding a file; a new area gets a new prefix rather than a bare name.
- `server/internal/web/`: `go:embed`ed `html/template` files and static assets (CSS/JS), served at `/static/`.
- `server/internal/database/migrations/`: numbered up/down SQL migration pairs — the real schema source of truth.
- `server/internal/database/queries/`: hand-written SQL; `server/internal/sqlcgen/` holds the `sqlc`-generated Go bindings (never hand-edited).
- `server/internal/auth/`: sessions, passwords (bcrypt), login lockout, password-reset tokens, email-verification tokens.
- `server/internal/csrf/`: double-submit-cookie CSRF middleware.
- `server/internal/i18n/`: default-category display names, keyed by slug.
- `server/internal/format/`: display formatting (money, dates, device labels) — no request, no DB.
- `server/internal/txnrule/`: the numeric limits a transaction has to satisfy regardless of entry path (form, inline edit, CSV import).
- `server/internal/pgval/`: pgtype wrapper helpers.
- `server/internal/csvimport/`: CSV sniffing/mapping/planning, no database access.
- `server/internal/mailer/`: Brevo HTTP API client for transactional email.
- `server/render.yaml`: the Render Blueprint describing the one web service deploy.

## Request and Response Conventions

- Responses are HTML, not JSON — this backend has no API consumers of its own; every mutation handler returns an HTML fragment htmx swaps into the DOM, or (for a full page load) a complete rendered page.
- Three render entry points in `server/internal/handlers/view_render.go`: `render` (full page + nav), `renderNamed` (a named sub-template that still needs the shell's shared fields), `renderFragment` (a named sub-template with no shell data at all).
- Every render call takes a struct, never a `map[string]any` — a missing field is a compile error instead of a silently blank row.
- Mutation handlers that touch the header balance return `header_balance_oob` as an out-of-band swap alongside their main response, since both nav bars render that widget and must stay in sync.
- htmx conventions: see `.claude/rules/htmx-conventions.md`. CSRF: every mutating request must echo the `csrf_token` cookie back via header (`X-CSRF-Token`, htmx) or hidden form field — see `.claude/rules/csrf.md`.
- Localization: none — the UI is English-only by design. Only default-category *names* are resolved through `server/internal/i18n`, keyed by a stable slug rather than the displayed string.

## Authentication Model

- Plain email+password login, no OAuth/SSO. Sessions are server-side rows in `sessions` (`server/internal/auth/session.go`), identified by an opaque cookie (`SESSION_COOKIE_NAME`), not a signed JWT.
- Sessions last 7 days (`sessions.expires_at`). A password change deletes every *other* session for the user but keeps the current one; "Log out everywhere else" in Settings calls the same deletion deliberately, as a user action rather than a side effect.
- Login lockout: 5 consecutive wrong passwords lock the account for 15 minutes (`users.failed_login_attempts`, `users.locked_until`), checked *before* password comparison so a locked account can't be used to extend its own lock. A completed password reset clears it.
- Password reset: `password_reset_tokens`, 1-hour TTL, single-use, emailed via Brevo.
- Email verification: `email_verification_tokens`, 24-hour TTL, shared by both signup confirmation and a settings email change (via `pending_email`, promoted onto `users.email` only once its own link is visited). Verification gates nothing — see Important Reality Checks.
- Account deletion is a hard delete (transactions → the account's own categories → the user row, in one transaction), not a soft `deleted_at` flag — see `.claude/rules/account-deletion.md`. The freed email can be re-registered immediately.

## Authorization Model

- There is no role or permission system. Every authenticated request is scoped to `auth.UserIDFromContext(ctx)`, and every query touching `transactions`, personal `categories`, or `sessions` filters by that user's own `user_id`.
- The only "shared" rows in the whole schema are the default categories (`categories.user_id IS NULL`) — readable and usable by every account, never writable by any of them.
- If a future feature needs per-user access tiers (an admin view, a shared household budget), there is currently nothing to build on — that would be new infrastructure, not a flag to flip.

## Core Data Model

- `users` — email (unique, login identity), password_hash (bcrypt), name, username (unique, `^[a-z][a-z0-9_]{2,19}$`), theme (`auto`/`light`/`dark`), email_verified + pending_email, failed_login_attempts + locked_until.
- `sessions` — id (opaque token, primary key), user_id, expires_at, created_at, user_agent (nullable — predates migration 000012).
- `categories` — user_id (NULL = shared default, else a personal category), name, type (`expense`|`income`), color (fixed 9-value palette via CHECK), slug (NULL for personal; a stable, unique, language-independent key for the 9 shared defaults — **match on this, never on `name`**). Unique index on `(user_id, type, name)`.
- `transactions` — user_id, category_id (FK to `categories`, **no `ON DELETE` clause**, deliberate — see below), amount (BIGINT, `CHECK (amount > 0)`, VND as a whole-number integer), type (`expense`|`income`), description, occurred_on (DATE).
- `password_reset_tokens`, `email_verification_tokens` — single-use token tables, FK to `users` with `ON DELETE CASCADE`.
- **`transactions.category_id` and `categories` have no `ON DELETE` clause between them, on purpose** — a category can't be deleted while transactions reference it without the app reassigning those rows first. Every migration that touches `categories` (000006, 000008, 000014) is written as an in-place UPDATE for exactly this reason.

## Transaction & Category Domain Rules

- A category's `color` must be one of the fixed 9-value palette (8 user-selectable plus 1 reserved gray for "Other"); enforced by a CHECK constraint, not just the UI.
- A user cannot have two categories of the same `type` sharing a `name` — enforced by a unique index, `(user_id, type, name)`; NULL `user_id` rows (the shared defaults) are exempt, since Postgres treats NULL as always-distinct in a unique index.
- `amount` must be a positive integer (VND, no decimals) — enforced both by a DB `CHECK` and by `server/internal/txnrule`'s shared limits, which the add form, inline edit, and CSV import all read from the same place rather than each re-stating the limit independently.
- A default category is identified by `slug`, never by `name` — the single most-repeated rule in the codebase (see Core Data Model above and `server/internal/i18n.CategoryName`).
- CSV import is all-or-nothing by design, never partial — see `.claude/rules/csv-import.md` for why.

## Seeder Reality

- There is no separate seeder step or seeder framework — default data is seeded by the migrations themselves, applied automatically at startup.
- The 9 shared default categories went through three migrations, not one: 000005 inserted an 8-category placeholder set; 000006 redesigned it in place to the current 9-category palette (renaming/recoloring existing rows rather than delete-and-reinsert, specifically so any account with history wasn't broken); 000008 gave each default its stable `slug` and renamed the Vietnamese display names to English.
- One historical wrinkle to know about: 000006 deleted the old "Thu nhập khác" (generic other-income) default *only if no transaction referenced it*; any account that already had one still has that row. 000014 re-adds an `other_income`-slugged default for the same conceptual slot, specifically because email ingestion needs an "I don't know" bucket on the income side. Do not "clean up" either of these without checking whether it would orphan a real transaction.
- Conclusion: before touching a migration that inserts, updates, or deletes a default category, read 000005, 000006, 000008, and 000014 together — the current shape only makes sense as their sum.

## Setup and Run

- Backend install/run:

```bash
cp .env.example .env
go run ./cmd/server
```

- Requires `DATABASE_URL` etc. in `.env`, pointed at a locally installed Postgres (no Docker/compose setup is shipped, intentionally). `main.go` loads `.env` itself via `godotenv`; a variable already set in the environment still wins over the file.
- Migrations apply automatically at startup — there is no separate migrate step, for a fresh database or an already-migrated one restarting.
- Run tests (DB-touching tests are skipped unless `TEST_DATABASE_URL` is set; point it at a scratch database):

```bash
TEST_DATABASE_URL="postgres://USER:PASSWORD@localhost:5432/expense_tracker?sslmode=disable" go test ./...
```

- Checks that must stay clean before any commit:

```bash
go build ./...
gofmt -l .        # must print nothing
go vet ./...
```

- Regenerate `server/internal/sqlcgen` after changing SQL in `server/internal/database/queries` or the migrations:

```bash
sqlc generate
```

## Environment Variables That Matter

- `DATABASE_URL`, `PORT`, `SESSION_COOKIE_NAME`, `SECURE_COOKIES` — core wiring; `SECURE_COOKIES=true` is required once served over HTTPS, or the session cookie is silently refused.
- `APP_BASE_URL` — absolute link base for the password-reset email; defaults to `http://localhost:$PORT`.
- `BREVO_API_KEY`, `MAIL_FROM` — password-reset/verification email, sent over Brevo's HTTP API rather than SMTP, because Render's free tier blocks outbound SMTP ports but never 443. Optional — blank leaves forgot-password working end to end except the actual send, which is logged instead.
- `JWT_SECRET` — signs/verifies access tokens (`internal/auth/jwt.go`, Phase 1 of the Gin/React migration — see `CLAUDE.md`'s "Migration in Progress"). Required, no fallback, same reasoning as `DATABASE_URL`: `config.Load()` refuses to start without it rather than sign tokens with a key baked into the source tree.
- `CORS_ALLOWED_ORIGINS` — comma-separated origins the (future) Gin API's CORS middleware accepts credentialed cross-origin requests from. Optional; blank means none, correct until `client/` has a real deployment to allow.

## Deploy Notes

- Production target is a single free Render web service on Render's native Go runtime — **no Dockerfile, by design** (see `server/render.yaml`'s own comments).
- Database is Neon Postgres, not Render's own free tier (which is deleted after 30 days). `DATABASE_URL` in Render must be Neon's *direct* (non-`-pooler`) connection string — golang-migrate's session-level advisory lock isn't supported by the pooled endpoint.
- `autoDeploy: true` on `main`; a schema change ships with the same push since the server migrates at startup. `rootDir: server` makes Render `cd` into `server/` before running `go build -o server ./cmd/server` / `./server`, so the binary is built into and run from `server/` (not the repo root) — migrations are read from a path relative to that working directory even though templates/static assets are `go:embed`ed.
- `/healthz` doubles as the Render deploy health check and the target of an external cron that pings it every ~10 minutes to stop the free instance spinning down after 15 minutes of inactivity.

## Safe Edit Rules For Agents

- Never identify a default category by its displayed `name` — match on `slug`. This is the one rule repeated everywhere in this repo on purpose.
- Never delete-and-reinsert a default category in a migration; `transactions.category_id` has no `ON DELETE` clause, so any account with history would break. Update rows in place (see migrations 000006/000008/000014 for the pattern).
- Preserve the render-entry-point contract in `view_render.go` (struct, never a map) when adding a new page or fragment — a map silently swallows a missing field instead of failing to compile.
- When touching auth, re-check that CSRF, session expiry (`HX-Redirect` on an htmx request, never a raw redirect), and the lockout window all still agree — these pieces interact more than their separate file locations suggest.
- Follow `.claude/rules/go-conventions.md` for style; it is the one rules file that applies to every `.go` file in the repo.

## Common Task Playbooks

- Add a new authenticated page or fragment:
  - add the route in `server/internal/handlers/app_router.go` inside the `auth.RequireAuth` group
  - add the page's template set to `pageTemplates` in `server/internal/web/web.go` if it is a new page (not just a new fragment of an existing one)
  - use `render`/`renderNamed`/`renderFragment` as appropriate (see `.claude/rules/templates-static.md`)
  - if the handler mutates data the header balance depends on, return `header_balance_oob` alongside the main response
- Add a new default category: do not do it by hand. Add it through a migration that follows the 000006/000008/000014 pattern (in-place update, an idempotent insert guarded by `WHERE NOT EXISTS`, a `slug` from day one), and update `server/internal/i18n` and `.claude/rules/categories.md`.
- Add a new environment variable: add it to `server/.env.example` with a comment explaining what leaving it blank does, to `server/render.yaml`'s `envVars` (with `sync: false` if it is a secret), and to this file's "Environment Variables That Matter".
